# v0.3 Gap Analysis — 2026-10-07

## Purpose

This analysis identifies which remaining gaps justify changes to the provider-neutral core after:

- v0.1 safe-action lifecycle;
- v0.2 runtime hardening;
- Cloudflare production profile;
- end-to-end reference-agent validation across GitHub and TradingView.

The goal is to avoid speculative abstraction.

A gap belongs in core v0.3 only if it is:

1. cross-provider;
2. security- or correctness-critical;
3. already exposed by composition/production-profile validation;
4. difficult to solve consistently at the product layer.

## Findings

### Priority 1 — Trusted approval authenticity

**Status: MUST address in v0.3.**

Current approvals are structurally bound to an action proposal, but the core runtime trusts any object shaped like a valid `ApprovalReceipt`.

The reference-agent validation already exposed the underlying trust problem: the agent must not be able to mint its own trusted approval.

Moving issuance outside the agent fixes the example, but core semantics still lack a way to distinguish:

- a receipt produced by an authorized approval authority;
- a forged object with the same fields.

#### Risk

A compromised or incorrectly composed agent/application boundary could construct:

```js
{
  valid: true,
  actorId: "human-1",
  toolName: "...",
  actionSignature: "...",
}
```

and satisfy the current decision engine.

That violates the security invariant that approval authority must be independent from the actor requesting execution.

#### Recommended v0.3 direction

Introduce an **Approval Authority Port**.

Conceptually:

```text
proposal
→ approval authority
→ opaque/verifiable approval credential
→ runtime validation
→ decision
```

Core should not require a specific cryptographic scheme.

It should require an adapter contract such as:

- `issue(proposal, approverContext)`;
- `verify(credential, proposal)`;
- optional `consume(credential)`.

Reference implementation may use keyed signatures or an in-memory trusted authority for tests.

Production profiles may use:

- server-side signed credentials;
- database-backed approval records;
- session-bound approval tokens;
- Durable Object-backed claims.

The agent itself must never hold the authority secret.

---

### Priority 2 — Durable workflow identity and resumability

**Status: DO NOT implement as a general core engine in v0.3.**

The current workflow runner is correct inside one process invocation, but workflow state is ephemeral.

The Cloudflare profile has a D1 workflow table and Queues mapping, yet core does not define:

- workflow identity;
- durable step state;
- resume semantics;
- duplicate delivery handling;
- step idempotency across restarts;
- terminal vs resumable partial states.

#### Risk

A process restart or queue redelivery can cause:

- repeated completed steps;
- duplicate external side effects;
- loss of partial-state context;
- compensation executed twice;
- inability to determine whether a workflow is safe to continue.

This is no longer theoretical: asynchronous Queues and production runtimes inherently redeliver/restart work.

#### Revised direction after market validation

Do not build a general durable workflow engine or replay system. Temporal, Restate, Dapr, LangGraph, and OpenAI durable integrations already cover this class well.

Core should instead define only the minimum interoperability hooks needed to carry action-policy context across an external durable runtime.

Useful context fields may include `workflowId`, `stepId`, and pinned policy provenance, but checkpoint/replay/resume semantics belong to the selected durable runtime.

---

### Priority 3 — Policy/version provenance

**Status: SHOULD address, preferably alongside durable workflows.**

Current decisions record a reason but not an immutable identity of the policy/tool-contract version that produced the decision.

As policies evolve, audit records may become ambiguous:

> Was this action allowed under today's rules, or under the rules that existed when it ran?

#### Risk

This affects:

- incident investigation;
- reproducibility;
- compliance/audit;
- workflow resume after policy changes;
- interpreting old approval receipts.

#### Recommended direction

Add immutable provenance fields to proposals/decisions/workflows:

- `policyVersion`;
- `toolContractVersion`;
- optionally `runtimeVersion`.

A resumed workflow must explicitly decide whether to:

- continue under pinned policy;
- re-evaluate under current policy;
- stop for human review.

This should not become a generic versioning framework.

A small explicit contract is enough.

---

## Gaps that should NOT enter core v0.3 yet

### Distributed tracing / correlation IDs

Useful, but this is mostly observability plumbing.

Add a generic `correlationId`/context propagation field when needed, but do not build a tracing framework into core.

### Multi-party approvals

Important for some financial/security domains, but no current reference scenario requires quorum approvals.

Keep it as a future Approval Authority capability.

### Real provider capability drift

The current capability registry plus provider-specific discovery is sufficient for now.

Do not add a generic schema-negotiation framework until a real provider integration exposes a concrete failure.

### Human approval UI

UI/session behavior belongs to applications and deployment profiles.

Core only needs the approval authority boundary and verifiable credential semantics.

### Cryptography choice

Core should define trust semantics, not mandate HMAC, asymmetric signatures, JWT, or another credential format.

---

## Recommended v0.3 scope

v0.3 should remain deliberately narrow:

1. **Approval Authority Contract**
   - trusted issuer boundary;
   - verifiable approval credentials;
   - explicit consumption/replay semantics.

2. **Policy Provenance**
   - pin policy/tool-contract identity to decisions and approvals;
   - preserve evidence across external durable runtimes.

3. **Framework Interoperability Hooks**
   - minimal action context that can cross OpenAI Agents SDK, MCP, Temporal, Restate, Dapr, or LangGraph boundaries;
   - no home-grown workflow scheduler/replay engine.

These are one coherent theme:

> **portable trust around consequential agent actions.**

## Proposed lifecycle after v0.3

```text
DISCOVER
→ PROPOSE
→ DECIDE (policy version pinned)
→ REQUEST APPROVAL
→ VERIFY TRUSTED APPROVAL
→ EXECUTE
→ VERIFY
→ AUDIT
→ CHECKPOINT
→ RECOVER / RESUME
→ RESOLVE
```

## Recommendation

Do not add more provider adapters or agent features before these two core security/correctness gaps are resolved.

After v0.3, validate specifically against:

- forged approval credential;
- approval replay;
- policy version mismatch;
- OpenAI Agents SDK tool wrapper;
- MCP tool-call middleware;
- one external durable runtime (Temporal, Restate, or Dapr) carrying the same policy context.

If those scenarios pass, the runtime will have moved from a safe single-process/reference architecture toward a genuinely durable agent execution model.
